# Project flow intake

Use the shared workbench at `E:/project/Bdesign/work/project-workflow-blueprint`. If it has moved, locate the checkout containing `scripts/resolve-project-flow.cjs` and `documents/workflow/project-start.md`. Read the architecture entry, common redlines and project start guide there. Keep those rules in the workbench.

Apply common redline R01's source-edit boundary: source components, templates, variables, styles and specifications are read-only unless the user explicitly authorizes modifying those source objects. A source link or an instruction to adjust a target deliverable does not grant source-edit permission. Report source defects and proposed changes; continue within the authorized target scope without silently repairing the source.

1. Read the target project's applicable instructions, current adoption records and implementation. Use its project profile when present. For initial analysis without a profile, derive inputs from the existing evidence using the shared template. Retain unknown fields and distinguish proposed choices from adopted ones.
2. Identify each delivery surface independently. Record the key task, asset references, adoption basis and change type. For a component gap or base replacement, list the behaviors that must survive. Read the brand and component guide for UI surfaces.
3. Run the shared resolver with the profile path. For an unsaved profile, call its exported `resolve` function with the proposed object. Use its result as guidance and check references against actual project evidence. If Node or the resolver is unavailable, apply the startup guide directly and state which checks were manual.
4. Return each surface's branch, evidence, blocking decisions, next action and one representative verification path. Separate missing input from decisions needed for the current task. Apply the user's existing authorization to any subsequent work.

For an agreed brand and a local color change, follow the existing Token. For a new brand direction or a missing design rule, consult the workbench brand guide's optional design research branch. Keep draft design recommendations separate from adopted rules.

When one user plans parallel development of the same project across multiple AI windows or agents, read "按需分支：多AI窗口并行开发" in `documents/workflow/development.md`. Evaluate task dependencies before splitting work; record isolated workspaces, shared-change ownership, handoff and integration evidence in existing project tasks. This routes the workflow; it does not itself dispatch windows, lock files or authorize additional agents.

For design-source intake, read the conditional branches in `documents/workflow/design.md`. Route missing Tokens to source-based extraction, and external layouts with existing Tokens to semantic adaptation. For maintained Figma designs with reusable components, include design-component identity, properties, Token bindings and the code contract in the existing mapping record. Keep unimplemented contracts and verified code mappings distinct. Select the scope from actual reuse needs. Use the available Figma skills for file operations and report tool access and unverified bindings explicitly.

For design reproduction, style migration or theme replacement, also apply the guide's conditional style-feature mapping and visual acceptance checks. Identify the required characteristics before mapping; choose Tokens, styles, components, structure or assets as appropriate. Track unresolved features in the existing record, and do not treat variable binding coverage as visual acceptance. Keep concrete visual values project-specific.

For a reference website used to establish a reusable style system and extend missing layouts or components in Figma, read `documents/workflow/website-style-extraction.md`. Follow the source-sampling, editable calibration, rule extraction, extension and validation path. Scale the sampled pages to the visual coverage needed by the requested output.

For extracting a design draft or packaging a maintained Figma design library, use the "设计资产草稿与规范库封装" branch in `documents/workflow/design.md`. Select draft or library packaging from the requested outcome. Discover actual documentation-template components before choosing instances; keep product Tokens separate from documentation presentation. Reuse existing asset identities, validate new candidates in the design source before approved promotion, and record source-of-truth and diff-based return synchronization. Deliver publication candidates within scope; distinguish structural, visual, publication and cross-file reuse evidence. Do not impose a project's template or component base on other projects.

For design-spec or Token-library documentation generation, read that branch's "规范文档生成约定（内部执行入口）", especially "设计规范呈现契约（2026-11-08）" and "当前模板登记与项目采用", before writing. Use the registered Figma page header with a short visible description, and the user's title/description/content module components. Read actual source spacing and public properties instead of reconstructing them from screenshots. Design specs contain observed parameters only: keep missing requested categories or scale positions blank; do not invent values, merge unrelated specification headings, or add process/source commentary. Keep Token generation and semantic mapping separate unless explicitly requested. The central guide owns these rules and source/target identity records; do not duplicate its visual parameters in this skill. Derive names from project responsibilities and the existing vocabulary, preserving deduplication and asset identity.

For parameter presentation, classify text colors within the neutral or brand-tinted neutral palettes, never as a duplicate text-color category. Use one observed opacity ladder per base color across font/background/stroke uses; separate ladders only when the base color changes. Group typography by actual font size, render size specimens at that size, retain observed weights and their line-height/letter-spacing combinations, list alternate observed line heights with `/`, and describe actual usage. Combine observed padding, margins and gaps in one spacing specification, classified by observed element, card, content, module or page scope; deduplicate and sort within each category. Classification does not introduce semantic Tokens or directional application recipes. Deduplicate borders by direction, thickness and inside/center/outside alignment; color, opacity and gradient differences belong to color documentation and do not create border tiers. Apply the central guide's full presentation contract, including missing-value placeholders and font-availability limits.

Background-blur specifications require both a visual specimen and a parameter table showing the actual blur type, radius with units, and other observed source parameters. This is an explicit table exception; never substitute illustration-only values or assumed defaults for product parameters.

Spacing specifications include padding, margins and gaps in one document. Classify observed values by element, card, content, module and page scope as applicable; a value may occur in multiple evidenced categories, but is deduplicated and sorted within each. Use standalone filled rectangles whose widths equal the observed values, with value/unit underneath, a shared presentation-only height and horizontal wrapping. Do not use flanking blocks, repeated bordered cards, four-side application combinations or a duplicate padding document. Do not infer categories solely from numeric thresholds. User examples guide presentation, not parameter values. Follow the central guide for missing values and visual hierarchy.

For design-spec presentation, omit decorative typography and radius-card/specimen borders. Classify radius scales by actual element/card scope, deduplicate and sort within categories, and show only category headings, smaller specimens with unchanged observed radii, and values/units; omit redundant per-item labels or usage descriptions. Keep category sections 120px apart as documentation spacing. Omit body headings that merely repeat the page topic or add “scale”; retain meaningful categories. Follow the central guide for presentation details; none of these layout choices are product parameters.

For icon generation, each icon has exactly one safety frame. Do not nest an icon safety frame inside a second same-purpose wrapper; when a button already supplies the size and alignment frame, place the glyph directly within it and retain button interactions. Keep glyph sizing independent from frame sizing, and document stroke, corner treatment and visual insets.
