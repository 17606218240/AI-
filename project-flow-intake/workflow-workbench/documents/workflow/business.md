# 业务需求分析 · 通用流程定义

范围：通用流程草案，尚未安装为Codex Skill。修改后不自动影响已有项目的采用版本。

## 工作流总表

五个业务节点定义产物和进入条件。六个接入阶段提供逐端判断、验证和交接方法。P0–P2 指本轮业务流程补充。

| 接入阶段 | 对应业务节点 | 产出 | 分流 | 验收与交接 | P0–P2 与 Skill 状态 |
|---|---|---|---|---|---|
| 1. 接入 | ① 需求接入 | 需求摘要、项目配置、当前基线、已有资产与本次改动 | 新项目梳理目标与用户。已有项目先查决定、源码和交接记录 | 明确目标、任务和本轮范围。记录关键缺口，再逐端判断 | P2 按需澄清。接入由 `$project-flow-intake` 支持 |
| 2. 判端 | ① 需求接入 → ② 首期业务与竞品分析 | 逐端清单，含用户、任务、运行环境与交付方式 | B/C 按用户和任务判断，Web、App、小程序按运行环境判断 | 每端的任务与约束交给首期分析，支撑竞品对照和范围取舍 | 判端与逐端检查重点已纳入 `$project-flow-intake` |
| 3. 定范围 | ② 首期业务与竞品分析 → ③ PRD、页面与验证 | 业务分析、竞品与替代证据、MVP 范围、PRD 与验收标准。财务和风险材料按需输出 | 区分首期、先验证与后续保留。明确的小改动沿用当前基线 | 对齐规则、页面、验证和任务，再交逐端方案评审 | P0 一致性检查。业务分析与 PRD 由现行业务流程承接 |
| 4. 分流与定方案 | ③ PRD、页面与验证 → ④ MVP 可执行性评审 | 逐端建议分支、依据、待决事项及代表验证路径 | 按需走组件复用、Token 调整、组件缺口、基座替换或品牌探索。无界面服务走服务验证。设计缺口可用 UI UX Pro Max 补候选 | 写明验证输入、操作、预期和前置条件，交下一步执行 | `$project-flow-intake` 输出分支建议与验证路径。品牌评审按需调用 |
| 5. 验证代表路径 | ③ 验证计划 → ④ MVP 可执行性评审 | 实测结果、失败证据、待验证项和可执行性结论 | 范围变化回②，规则变化回③，实现偏差在④核对影响后交⑤ | 结果回填原验证项，标记通过、失败或证据不足，并记录验证层级 | P1 验证回流。验证执行尚未单独封装 |
| 6. 交接与迭代 | ⑤ 定版与开发交接 | 已采用版本、逐端分支、证据、待办与下一步，必要时附逻辑图 | 定版后按当前基线登记差异。明确采用后合入正文，实施遵循已有开发授权 | 复核规则、行为、证据与待办，新对话凭交接记录接手 | P0 交接复核与 P1 变更管理。接手可用 `$project-flow-intake`，归档尚未单独封装 |

## 节点

### 1. 需求接入

用户输入：提供一句需求或首批资料；说明已知目标和限制。

分析：识别起点、用户、任务与成功结果；已有项目核对当前业务/开发基线，保留可用成果。；检查来源正文完整性、正文版本与引用关系；区分事实、用户决定、推断和未知，关键主张登记来源、日期与适用场景。

产物：需求摘要；来源/主张登记（版本、定位、完整性、证据状态）；关键缺口。

确认：仅当目标或关键边界不清时，确认理解与分析范围。

进入条件：目标和起点清楚；来源冲突与缺失已标记，未将历史自述视作当前完成证明。

接入时先查现行决定、源码和交接证据。若仍有会改变本轮范围、成本或验收的问题，集中提出，并说明不同答案会改变哪条路径。选项有实质差异时给出两至三个方案及建议。已有明确答案直接引用。可逆且影响小的判断可记录假设继续验证，后续范围的未知保留到对应阶段。

### 2. 首期业务与竞品分析

用户输入：补充关键证据；没有的数据可明确未知。

分析：形成商业、财务与风险三类结论，已有合格文档补差；风险从接入识别，结论相互校正。；财务参数登记一次：来源、公式、营运周期、固定/变动/一次性成本与工时；情景重算，其他文档引用对应条目。；核对服务承诺与人员覆盖、现场责任及支持成本；缺依据的结论保留为假设。

产物：业务分析说明（含风险）；涉及商业或资源投入时补充财务BP；复杂风险单列备忘

确认：确认核心业务方向、首期边界、预算假设与优先验证风险；不逐份机械确认。

进入条件：关键成本可复算，承诺与资源有对应；重要矛盾已处理，或明确验证任务及负责人。

### 3. PRD、页面与验证

用户输入：确认首期分析结论；选择这期解决的核心任务。

分析：用范围/验收矩阵对齐本期启用端、角色、任务、优先级和验收层级，明确后续项。；定义正常与关键异常；区分请求受理与实际执行、失败/超时/未知。降级逐项标保留/失去能力、人工替代及新验收。；验证计划逐项关联假设、证据、样本/周期、通过/失败/不确定及决策；单例不推断总体或长期效果。

产物：01项目_PRD（含范围/验收矩阵）；灰度／验证执行方案（假设与证据对应）；必要草图与未决事项

确认：确认PRD版本、MVP范围、验收目标与验证方式。

进入条件：优先级与本期验收无冲突；关键异常、降级差异和验证口径可追踪。技术实现策略交给开发约束分析。

### 4. MVP可执行性评审

用户输入：在候选范围中明确本期选择；确认能接受的验证层级。

分析：按本期目标核对人员、数据、接口授权、环境、预算及现场条件，给出继续、缩小、先验证或暂停的结论。；探索、Mock、真实试点与商业效果分别要求对应证据；只处理当前批次阻塞，不以远期条件阻断已授权任务。；新增需求评审排期；阻断当前验收的缺陷暂停相关验证，限定修复、回归并更新结果，不一律推到下版。

产物：MVP可执行性结论；依赖与缺口表（影响、负责人、验证方式、复核时间）

确认：确认本期执行层级与取舍；仅有重大范围/风险变化时定向复核，已有明确授权可沿用。

进入条件：结论有对应证据，失败/不确定有回退路径；Mock通过不推导真实联调或商业验证通过。

### 5. 定版与开发交接

用户输入：确认交接业务版本与范围；开发采用决定在下一模块明确。

分析：复杂流程按确认的PRD生成必要逻辑图，核对图文、范围及状态一致。；交接包引用已登记的版本、参数、证据与决定；只补交接清单，不重抄整套文档。

产物：按需逻辑图；交接文档索引与版本/决定记录

确认：核对交接完整性；仅对新增差异或未确认取舍补决定，不重复确认同一内容。业务新版本不自动改变开发目标。

进入条件：交接清单齐备，可进入开发约束分析；实际编码还需明确约束与开发采用版本。

## 产物规则

### 定版后的变更与验证回流

在原评审或交接记录追加一条变更，引用当前有效基线和规则编号。记录新增、修改或删除的内容、原因、影响的页面与验收、负责人及下一步。若实测偏离既有规则，登记缺陷；若预期行为本身尚未决定，标记待采用的规则细化。保留原基线和历史证据。

验证后把结果回填到原验证项，写明通过、失败或证据不足及对应的继续、缩小范围、补证或暂缓决定。影响业务方向或首期范围时回节点 2。影响规则或验收时回节点 3。发现实现偏差时回节点 4 核对阻塞范围，并将修复与回归接到节点 5 的交接待办。

交接前按受影响条目核对「规则 → 页面或服务行为 → 验证证据 → 实施待办」。待采用的差异在明确采用后合入对应正文，交接记录保留决定与来源。已有开发授权按其范围执行。

- 业务分析说明（可采用商业计划书形式）：必须覆盖用户、问题、价值、范围；可直接更新已有文档，不强制另建BP。 用户、问题证据、价值与替代方式、业务闭环、首期范围。
- 02运营财务BP：涉及收费、预算、运营投入或商业可行性时独立输出；轻量工具可合并为投入收益小节。 参数、来源、公式与周期，固定/变动/一次性及工时成本，情景计算；财务数据唯一维护处。
- 03风险与成本控制备忘：风险分析必须覆盖；简单项目并入业务分析，复杂项目独立成文。 触发、影响、责任、应对和复核；引用财务参数，不另维护重复预算。
- 01项目_PRD：首期分析确认后定稿；有来源和版本。 本期范围/验收矩阵、角色流程、异常/执行结果和降级差异；引用确认的业务结论。
- 灰度／验证执行方案：随PRD形成；按项目采用用户测试、Mock或真实试点。 假设→证据→样本/周期→判定→决策；明确阻断缺陷处理与回退，引用PRD验收。
- 正式逻辑图与业务交接包：按流程复杂度选择图表；交接清单引用原文件，不复制一整包正文。 分层逻辑图、确认版本、范围、验收、依赖、未知与决定。
- 项目评审PPT：有评审会议或用户要求时输出；不作为所有项目的必经门槛。 为什么做、为谁做、首期做什么、证据与风险、资源计划及待决定事项。

## 业务研究的执行顺序（2026-11-03）

保留五个主节点，在节点内明确研究阶段；不是每个阶段另造一份文档。

| 顺序 / 位置 | 必须先弄清 | 分析与产出位置 | 通过条件 |
|---|---|---|---|
| 1 需求接入 | 为谁、什么场景、现有怎么做、成功是什么 | 原始资料与业务分析开头；未知明确标记 | 不把BP主张当用户事实 |
| 2A 首期业务分析：用户与替代方案 | 实际任务、频率、痛点及现有替代 | 先比较手工、表格、不做和同类产品；竞品按任务选，不按知名度堆名单 | 有问题证据；缺真实访谈时注明是假设 |
| 2B 首期业务分析：竞品与可行性 | 哪些任务已有成熟处理，差异是否有价值 | 在业务分析原文写来源日期、平台/版本、可观察事实、项目启示、限制；接着测算投入与风险 | 先得出方向和首期边界，再定PRD；不得把竞品功能直接纳入本期 |
| 3A PRD：业务模型 | 角色责任、对象、规则、状态、数据口径与异常 | 在PRD对应功能处写明输入、处理、输出、权限、统计影响及验收 | 关键业务闭环可演算 |
| 3B PRD：页面与交互复核 | 已有任务如何落到页面，哪里跳转、哪里页内完成 | 针对关键路径再研究产品交互；列独立页/页内/弹窗/系统交互，核对返回、草稿和失败 | 有页面数量、功能归属和跳转依据；低保真任务走查尚未执行就写待执行 |
| 4 MVP评审 | 依赖能否取得，当前范围能否执行 | 原PRD与验证计划就地补资源、许可、样本、成本、降级与未决 | 区分公开说明、模拟、真实使用、真实服务验证 |
| 5 定版交接 | 采用哪版、哪些结论仍是提案 | 引用当前有效文档与决定，不重复正文 | 新研究不自动改变已采用范围或启动开发 |

既有项目从当前基线补缺，不退回重做全部BP。影响范围的新发现回到2B，只有交互问题回到3B。无直接竞品时分析替代方式，不为凑数硬找；资料无法取得时写搜索范围与限制，不虚构结论。

## 除竞品外必须检查的业务依据

| 依据 | 支撑什么决定 | 放在哪里 / 如何取得 |
|---|---|---|
| 用户与场景 | 需求是否真实、主要任务和使用频率 | 业务分析；访谈、现有记录、观察。个人工具可先由本人真实任务验证，不冒充市场样本 |
| 业务对象与规则 | 谁能做什么、何时生效、失败如何处理 | PRD对应功能；实例推演、领域资料与有效用户决定 |
| 数据定义与质量 | 单位、时间、缺失、来源、计算、去重及图表是否一致 | PRD统计与数据章节；真实样本、边界样本、公式核算。未知不填零 |
| 资源与专业内容 | API、内容、模型、授权是否真的可用 | 所属能力章节；核实接口/许可/成本，再作授权范围内验证。公开阅读不代表可复用 |
| 资源投入与收益 | 首期是否值得和做得起 | 业务分析或财务BP；个人工具分析时间、录入负担和维护成本，非商业项目不硬造营收预测 |
| 使用环境与可用性 | 操作能否完成、信息是否看懂 | PRD与验证计划；设备/浏览器、低保真关键任务走查，不能用竞品页面替代本项目验证 |
| 隐私与生命周期 | 收集必要性、留存、删除、恢复、导出责任 | PRD对应规则；按实际数据与部署方式分析，不套无关合规清单 |

每条结论保留“来源或用户决定 → 事实/假设 → 对应需求/页面 → 验证与结果”的追溯。不要求全部都有数字；缺证据写未知，不能把模型推测包装成数据支撑。


## 竞品分析的具体执行

1. 定问题：本轮要决定定位、范围还是交互；先读当前采用版本。
2. 选对象：按核心任务选直接产品、邻近产品和人工替代；数量以覆盖差异为准，排除无关大而全功能。
3. 取证：优先官方资料和授权可用的实际产品；记录日期、平台、版本、免费/付费限制、具体路径与出处。没有登录实测不能写实测。
4. 对照：使用同一任务比较输入负担、处理规则、结果、异常/恢复和数据可追溯性，不只比较截图或有无功能。
5. 落决定：在业务分析/PRD对应章节写可借鉴、不适用、待验证及原因，关联功能/页面，不自动采纳新需求。
6. 验证：页面建议先走核心任务；尚无产品时用低保真，结果按实际证据记录。已批准的独立工作不因无关竞品缺失停止。

最小产出字段：问题、对象选择理由、来源/时间/平台、观察事实、推断、项目影响、限制、下一步。融入已有业务分析或PRD，不默认新增独立竞品报告。
