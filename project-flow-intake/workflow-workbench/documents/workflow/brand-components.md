# 品牌与组件选型

品牌方案适用于需要界面的端，双基座是 B 端 Web 可选方案。默认一个主基座；先在已采用实现上验证缺口，再决定是否增加库。

已有品牌与基座满足本次任务时，直接沿项目契约实施；只读本次状态/消费映射，不重复设计研究或候选选型。出现真实能力缺口、换基座或新品牌方向再启用对应分析；检查沿[增量验证](project-start.md#按需读取与增量验证)执行。

| 改动/场景 | 执行方式 |
|---|---|
| 只改普通底色 | 改已有语义角色，如 surface.canvas 或 surface.panel；仅一处例外用局部语义，不改 primary，不换库。检查文字/边框对比、悬浮和暗色模式 |
| 强品牌、基础行为 | 已有组件能通过语义角色实现就复用；新建 React Web 可评估 shadcn，验证焦点、键盘与状态 |
| B 端行为复杂、视觉可接受 | 已采用 AntD 时用公开 API 和主题能力，例如表格、树、日期；已有其他主库时先验证它及专用组件能否满足 |
| 强品牌、行为也复杂 | 对照真实代表路径比较官方主题、薄封装、专用组件和自建；不能假设 AntD 内部行为可任意拆出来重绘 |
| App / 小程序 | 按该端控件、系统主题及宿主能力映射，不引入 Web 双基座 |

层级：①品牌源（基础值 → 语义角色 → 需要时组件角色）；②端适配（Web CSS 变量、AntD theme、原生主题对象等）；③组件基座（提供实际行为）；④项目公共契约（只封装有迁移或一致性价值的组件）；⑤页面组合（消费契约并保留正常语义标签）；执行规则与验证贯穿各层。

一套语义源可输出多端主题，源文件按项目选 CSS 或结构化数据。品牌值可改，角色名是契约；新增/删除角色需核对调用点。映射由适配层维护，避免两库分别手工维护同义值。换色通常只改值；换基座需回归行为和契约，不能承诺只改 Token。

React Web 接入参考：[shadcn 语义变量](https://ui.shadcn.com/docs/theming)、[Ant Design 主题配置](https://ant.design/docs/react/customize-theme/)。AntD 按采用版本的公开接口映射；主题作用域还要看弹层、通知、暗色与容器。两个库共存先验证重置样式、焦点、键盘、弹层层级、体积、升级风险和默认交互一致性。避免依赖内部 DOM；无法用公开能力实现时缩小差异或换方案。

不以 150 行、5 个封装做通用门槛。采用决定写明缺口、候选、代表用例、实测结果、维护与替换成本、适用范围。检查命令来自项目真实脚本；至少说明实际执行了什么。无需为主题换色新增依赖、空目录或治理工具。

组件缺口按四步处理；缺口仅指完成已明确需求所必需的能力，不授权增加新的产品效果或功能，范围遵守通用红线R01。先查公共出口与实际调用，复用已满足需求的组件。若只缺局部状态或组合，在现有基座内补齐。若公开接口无法覆盖关键行为，再比较外部组件与薄封装。最后评估自建，并用同一组行为场景比较成本。替换基座时记录兼容性、迁移范围和可恢复的旧版本。

工作台文档表格是一个可查的示例。文档列表通过公共 `DataTable` 展示数据，共享组件已接受可选的行选择契约。只改页面背景时追踪实际消费的背景变量。需要在当前列表增加批量选择时，先核对既有契约能否满足，并检查禁用行、全选与半选。若需求是跨分页保留选择，先定义选择范围与失败恢复，再评估能力缺口。此例依据现有源码，跨页选择是评审输入。

## 按需设计研究

判端和定范围后，若只有参考风格，或现行品牌规范缺少某个组件的状态定义，可查询 UI UX Pro Max 的风格与 UX 资料。输入目标端、已采用约束、缺失组件及必须保留的行为。把输出与现行规则对照，记录可采纳的检查项与验证方法。已有规范足以解决的换色和复用任务直接按项目规则处理。

毛玻璃日期选择器对照采用 [UI UX Pro Max 固定源码](https://github.com/nextlevelbuilder/ui-ux-pro-max-skill/tree/b7d5353e0130feb8c5574ef1251f8a1db1873ccb)。在临时目录运行 `search.py` 的 `ux` 和 `style` 查询。基线已要求用语义 Token、保留键盘与焦点并提供实色降级。查询补出了日期格式避免歧义、浮层内焦点可见且不被固定区域完全遮住，以及检查透明表面在不同背景下的文字对比。把这三项加入代表路径，在候选控件中分别检查读写日期、打开与关闭浮层、深浅及图片背景下的可读性。

查询里的白色透明度、模糊半径和示例焦点颜色保留作参考。实际值沿用项目品牌，实色降级由项目验证。试用证据覆盖检索与方案对照，日期组件的运行验收留给采用该方案的项目。

## 端型默认 Token 与验收

启动解析器按交付端返回默认预设和建议适配方式。B 端 Web 默认提议 `ant-web-default`；C 端 Web、移动 Web、安装 App、小程序分别有独立预设；服务端不返回界面预设。项目已有采用依据时，在该端的 `designPreset` 显式指定项目预设。解析结果用于接入，采用时在项目记录中锁定预设 ID、版本及适配器。

预设位于 `src/design-presets/`。颜色、表面、文字、边框、圆角、间距等角色共享，实际值和个别组件语义由项目维护。默认 Ant 预设取自本地 6.6.6 的公开全局 Token，侧栏和步骤尺寸是本工程的角色映射。组件专属默认样式仍由 Ant 提供。工作台只覆盖所需值，改 `workbench.json` 后重新构建。Ant 的 ConfigProvider、公开语义区域和页面 CSS 变量由适配层消费预设。

回写验收按已采用的规范逐条核对浏览器最终值和交互。侧栏检查容器透明与选中提示；弹窗检查标题、正文、底栏的独立间距与滚动。重要规则写独立的预期值，避免误改 Token 时预期与实现同步出错。原生 App 和小程序需由各自工程映射并在目标端验收。

### 组件状态验收

复用组件时明确状态来源、行为所有者和视觉 Token。菜单至少核对默认、悬停、选中、键盘焦点、禁用；选中与悬停叠加也要检查。页面提供当前路由或禁用条件，组件基座负责键盘和禁用行为，项目维护状态视觉。回写时在两套预设下检查实际计算样式及路由、折叠行为。业务没有禁用项时用隔离样本验证，报告注明覆盖范围。
